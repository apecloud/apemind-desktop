# 个人空间可选合同

本文给出 ApeMind Desktop、ApeMind CLI 和 ApeMind 服务端共同遵守的个人空间合同。它回答一个问题：当线上新账户默认没有个人空间、历史账户可能仍有个人空间、未来个人空间可能完全退出时，登录、选空间和数据操作应怎样保持一致。

## 产品基线

线上新账户默认关闭个人空间。过渡期内，历史账户可能有一个仍可用的个人空间、一个空的个人空间、一个或多个组织空间，或者没有任何工作空间。个人空间长期退出后，完全没有个人空间仍是正常账户状态。

个人空间存在、个人空间存在但为空、个人空间不存在是三个不同结果。登录成功只证明身份已经建立，不证明存在数据命名空间；空知识库也不等于没有个人空间。登录、刷新、账户信息和凭据撤销在没有工作空间时仍应可用。

## 统一发现和选择合同

`GET /api/v2/me/workspaces` 是唯一的工作空间发现来源。服务端返回的 `id`、`type` 和 `status` 是客户端可以保存和传递的 canonical 值。个人空间只有在服务端 presence resolver 确认仍可用时才出现在列表中。

`items: []` 是已认证但没有可用工作空间的成功响应。缺少 `items`、`items: null`、非数组、空 ID、空状态和未知类型属于 `invalid_response`；客户端应保留旧选择并提示刷新或升级，不能把坏响应当成空列表。

客户端不得根据用户 ID、`personal:<user_id>` 前缀、旧资格字段或知识库列表推断、拼接或恢复个人空间。多个 active 空间时不能静默选择数组第一项；只有一个空间时可以便捷自动选择。失效的历史选择必须清理并要求重新选择。

## 认证和数据边界

OAuth、API Key 和 MCP 都先建立身份，再由服务端实时校验 workspace、成员关系、资源权限和凭据绑定。没有工作空间、没有明确选择空间或 API Key 没有绑定空间时，workspace-aware 请求必须在限流、额度扣减、写库、幂等收据、后台任务和工具执行之前返回 `workspace_required`。

账户级查询可以继续使用；它们不能被解释成数据空间存在。未绑定组织的旧 API Key 只有在服务端明确返回仍可用的 canonical 个人空间时才可访问个人数据。组织 API Key 固定绑定一个组织，不能用 `--workspace` 或 `--all-workspaces` 扩大范围。服务端不自动创建隐藏 API Key、quota、Bot 或个人资源来填补空列表。

个人迁移、导出、删除、回滚、旧 alias 清理以及组织 Widget 授权属于独立项目。登录、刷新、客户端升级和组织 onboarding 不得隐式执行这些动作。

## CLI 和 Desktop 的职责

`apemind` 是 Agent 使用 ApeMind 的正式接口。`workspace list` 在空列表时成功返回空数组，`workspace current` 返回 `current: null`，数据命令返回机器可识别的 `workspace_required`、`workspace_stale` 或 `invalid_response`。`workspace use` 只能选择当前服务端返回的 active workspace。

Desktop 是 CLI 的图形化语法糖。登录、空间发现、空间切换、API Key 连接、错误解释和刷新都调用同一套 CLI 合同；Renderer 不复制授权逻辑、不拼接工作空间 ID，也不把登录快照当作实时权限证明。

没有工作空间时，Desktop 仍显示登录账户和刷新入口；知识库、模型、Agent、Chat、Turn 和其他数据页面显示“先选择或加入工作空间”的可恢复空状态，不发出猜测请求，不初始化个人资源。打包应用必须使用与 UI 合同一致的 CLI 版本，并在真实构建产物中验收空列表、唯一组织、多组织和失效选择。

## 六态验收

每个 workspace-aware HTTP/MCP 入口都要覆盖下面六种状态，并叠加 OAuth、组织 API Key、历史未绑定 API Key、成员撤销和当前选择失效：

| 状态 | 必须证明的行为 |
| --- | --- |
| 历史个人空间有数据 | 使用服务端返回的个人 ID 读取个人数据，组织请求不越界 |
| 历史个人空间为空 | 空知识库是成功结果，不删除或重建个人空间 |
| 新账户默认关闭个人空间 | 登录和账户级状态成功，不创建个人资源 |
| 个人数据已迁移 | 不返回个人项，旧资格字段不恢复个人空间 |
| 多组织账户 | 要求明确选择；聚合读取保留来源和部分失败 |
| 没有任何空间 | 发现命令成功，数据请求在副作用前返回 `workspace_required` |

## 剩余工作和收口顺序

| 顺序 | 工作包 | 收口证据 |
| --- | --- | --- |
| 1 | 服务端资源入口审计和副作用顺序 | 从真实 HTTP/MCP 入口证明 presence、成员和资源权限检查先于业务副作用 |
| 2 | CLI 空空间、失效选择、组织 Key、模型、通用 `api` 和 `--all-workspaces` | 编译后的二进制、结构化输出、稳定错误码和部分失败测试 |
| 3 | Desktop 打包应用验收 | 空列表、多组织、失效选择、恢复动作和内置 CLI 版本收据 |
| 4 | staging 和生产发布验收 | 发布版本、部署收据及六态线上验证；没有真实状态时明确标记未覆盖 |
| 5 | Widget 组织授权或下线 | 独立授权合同，或迁移、下线和已发布实例处置收据 |
| 6 | 个人数据迁移和最终删除 | 盘点、备份、演练、回滚窗口和人工授权 |

本合同的“已实现”只表示代码和定向测试具备相应证据；主干合并、镜像发布、部署完成和线上验收必须分别记录。局部绿色测试不能代表所有资源或所有环境已经完成。

## 不解决什么

本文不决定个人数据保留期限、删除日期、商业迁移政策或 Widget 的最终产品形态，也不授权生产数据迁移和删除。它只固定个人空间存在或不存在时的登录、权限、客户端和服务端行为。

## 读完后能回答的问题

- 没有个人空间时能否登录和查看账户状态？
- 空工作空间和空知识库如何区分？
- 工作空间从哪里发现，客户端为什么不能合成个人 ID？
- 哪些请求必须先选择空间，失败前哪些副作用必须尚未发生？
- Desktop 为什么只实现 CLI 的 UI，而不维护第二套业务客户端？
- 哪些工作仍需服务端、CLI、Desktop、Widget、迁移和发布验收？
