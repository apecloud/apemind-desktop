# 个人空间与组织工作空间最终合同

本文是 ApeMind Desktop、ApeMind CLI 和 ApeMind 服务端关于个人空间的当前定稿入口。它回答线上新账户已经默认关闭个人空间、历史账户仍可能保留个人空间、未来可能完全删除个人空间时，登录、空间选择、数据访问和发布验收应遵守什么规则。

服务端入口和副作用顺序以 [aperag-enterprise 的个人空间服务端合同](https://github.com/apecloud/aperag-enterprise/blob/main/docs/engineering-process/2026-09-26-personal-workspace-contract.md) 为准；跨客户端的调用边界和剩余工作以 [个人空间可选合同](2026-09-29-personal-workspace-optional-contract.md) 为准。本文固定两份文档之间的产品结论，后续实现和验收不得重新引入“个人空间一定存在”的假设。

## 当前产品事实

线上新账户默认没有个人空间。过渡期内，历史账户可能有一个仍可用的个人空间、一个没有知识库的个人空间、一个或多个组织空间，或者完全没有工作空间。长期完全没有个人空间是正常账户状态，不是登录失败、降级账户或需要客户端修复的异常。

个人空间的存在性只由服务端返回的工作空间集合决定。客户端不得根据用户 ID、`personal:<user_id>` 前缀、旧资格字段、知识库数量或管理员身份创建、恢复或推断个人空间。服务端不返回个人项时，CLI、Desktop 和插件都必须保持个人项缺失；登录、刷新、账户查询、凭据撤销和组织能力仍应可用。

## 三种存在性与统一响应

客户端必须区分以下结果：

| 结果 | 服务端表达 | 客户端行为 |
| --- | --- | --- |
| 个人空间存在 | `/api/v2/me/workspaces` 返回 `type=personal` 的 active 项 | 只使用该项的 canonical `id`；可以读取它实际有权访问的数据 |
| 个人空间存在但为空 | 返回个人项，读取该空间的知识库得到空数组 | 把空知识库显示为成功结果，不删除、重建或替换个人项 |
| 个人空间不存在 | 不返回个人项，可能返回组织项或 `items: []` | 不合成个人项；账户仍保持登录；需要空间的操作返回 `workspace_required` |

`GET /api/v2/me/workspaces` 是唯一的工作空间发现来源。明确的 `items: []` 是成功的“当前没有可用工作空间”；缺少 `items`、`null`、非数组、空 ID、空状态或未知类型属于 `invalid_response`，客户端应保留原选择并提示刷新或升级，不能把协议错误当成空列表。

工作空间选择只保存服务端返回的 canonical ID、类型和状态。重新加载后，服务端不再返回的旧选择必须清理；多个 active 空间不能静默选择数组第一项；只有一个真实返回的空间时可以便捷自动选择。任何数据命令在没有当前空间时都应在限流、额度扣减、幂等收据、写数据库、后台任务和工具执行之前返回机器可识别的 `workspace_required`。

## 长期边界

组织空间是长期的数据、权限和配额边界。个人空间只作为历史账户的兼容类型保留，未来可以完全移除。新功能不得依赖个人空间作为默认命名空间，也不得为了兼容界面创建隐藏 API Key、配额、Bot、模型或其他个人资源。

个人数据迁移、导出、删除、回滚和旧 `personal:<user_id>` 别名清理都是独立的数据项目。登录、刷新、客户端升级、组织加入和普通空间刷新不得隐式执行这些动作。个人空间完全退出后，组织登录、组织切换、Agent、CLI 和 MCP 能力仍按组织权限继续工作。

## 认证、连接和权限

OAuth、组织 API Key 和 MCP 调用先建立调用身份，再由服务端实时检查工作空间、成员关系、资源权限和凭据绑定。有效凭据不等于存在数据空间；账户级状态可以成功返回，但没有空间的 workspace-aware 请求必须返回 `workspace_required`。组织 API Key 固定绑定一个组织，不能通过 `--workspace`、`--all-workspaces` 或请求头扩大范围；未绑定的历史 API Key 只有在服务端仍返回 canonical 个人空间时才可访问个人数据。

CLI 是 Agent 的唯一正式能力面，Desktop 只是它的图形化语法糖。两者都只能消费服务端返回的空间项目和错误码；Renderer、Skill、`apemind api` 和 MCP 适配都不能复制授权逻辑、读取浏览器 Cookie 或从本地用户信息拼接工作空间。

## Desktop 产品行为

登录页应显示“可用工作空间”，不承诺一定有个人空间。登录完成但列表为空时，页面展示账号已登录、当前没有可用工作空间，并提供刷新、加入组织和帮助入口。知识库、模型、Agent、Chat、Turn 和其他数据页面显示“先选择或加入工作空间”的可恢复空状态，不发送猜测请求，也不初始化个人资源。

失效的历史选择在刷新后清理，并要求用户选择服务端重新返回的组织空间。切换组织只改变数据命名空间，不改变身份、连接、凭据或权限。Desktop 打包验收必须证明空列表、唯一组织、多组织、历史选择失效和恢复动作与 CLI 输出一致。

## 发布与验收口径

代码、定向测试、主干合并、镜像发布、部署和线上验收是不同证据层级。任何一层未完成，都只能报告对应层级的结果。每个 workspace-aware HTTP 和 MCP 入口都要在以下六种状态分别检查返回值、跨组织边界和副作用顺序：历史个人空间有数据、历史个人空间为空、新账户默认关闭个人空间、个人数据已迁移、多组织账户、登录后没有任何空间。

个人空间最终删除的完成条件包括数据盘点、导出和备份收据、可恢复的回滚演练、旧别名和 Widget 处置、停止创建个人资源以及人工授权。当前合同的完成不等于已经授权删除历史个人数据。

## 不解决什么

本文不决定个人数据的保留期限、商业迁移政策、删除日期或 Widget 的最终产品形态，也不授权任何生产数据迁移和删除。它只固定个人空间存在或不存在时的产品语义、接口边界、客户端行为和验收口径。

## 读完后能回答的问题

- 没有个人空间时，用户是否仍能登录、刷新和查看账户？
- 空个人空间与没有个人空间如何区分？
- 客户端从哪里发现空间，为什么不能合成个人 ID？
- 哪些请求必须先选择空间，失败前哪些副作用必须尚未发生？
- 代码、发布和线上验收分别凭什么证据判断完成？
