# 个人空间可选化与组织工作空间迁移设计

> 本文定义 ApeMind CLI、ApeMind Desktop 和 ApeMind 服务端在个人空间逐步退出期间必须遵守的统一合同。它补充并收敛 [ApeMind CLI-first 集成设计](2026-09-14-apemind-cli-first-integration.md)、[登录与工作空间设计](2026-09-12-apemind-desktop-login-v2.md) 和 [CLI 命令语义、权限范围与管理能力设计修订](2026-09-24-apemind-cli-command-scope-and-admin-design.md)。

## 现状

ApeMind 线上已经默认关闭新账户的个人空间。过渡期内，历史账户可能仍有个人空间，也可能只有一个或多个组织工作空间，还可能已经登录但暂时没有任何可用工作空间。长期产品方向是以组织工作空间承载数据、权限和配额，个人空间属于可迁移、可导出、可最终下线的遗留能力。

因此，工作空间不是“个人空间加组织空间”的固定二选一集合，而是当前身份在服务端实际可访问的命名空间集合。集合可以为空；客户端不能根据用户 ID 生成一个看似存在的 `personal:<user_id>`，也不能把站点管理员身份解释成组织数据访问权。

## 产品合同

登录成功只证明身份已经建立，不保证用户拥有工作空间。登录结果必须能表达以下三种状态：

1. 有一个遗留个人空间和一个或多个组织空间；
2. 只有一个或多个组织空间；
3. 没有任何工作空间。

工作空间发现以 `GET /api/v2/me/workspaces` 为唯一来源。响应中的 `personal_workspace_enabled` 表示历史资格和迁移状态；客户端仍然只消费服务端返回的 `items`。个人空间可以为空，服务端不返回个人空间时客户端不得补造；服务端返回空列表时，登录仍然成功，但所有需要工作空间的命令应返回可操作的 `workspace_required`。

默认空间选择遵循稳定、可解释的规则：

- 重新登录时，如果历史选择仍出现在 active 工作空间列表中，保留历史选择；
- 没有有效历史选择且只有一个组织工作空间时，自动选择该组织；
- 没有有效历史选择且没有组织、只有一个 active 个人空间时，为兼容旧账户选择个人空间；
- 有多个组织工作空间时不静默选择，要求用户执行 `apemind workspace use ID`；
- 没有可用工作空间时保留空选择，并提示用户加入组织或联系管理员。

“全部空间”是用户明确选择的聚合读取模式。它只遍历服务端返回的工作空间，不把不存在的个人空间加入结果；组织之间部分失败时必须保留来源和失败项。

## CLI 行为

`connection` 表示身份和凭据，`workspace` 表示当前请求的命名空间。两者独立：切换工作空间不会换账号，重新登录不会把无效的历史工作空间复活。

普通数据命令在没有当前工作空间时不得猜测目标，也不得退回个人空间。它返回结构化错误：

```json
{
  "error": {
    "code": "workspace_required",
    "message": "当前账户没有已选择的可用工作空间，请先运行 apemind workspace list。"
  }
}
```

`workspace list` 和 `workspace current` 可以在空选择状态下工作。`workspace use ID` 只能选择当前服务端已经发现且状态为 `active` 的工作空间；客户端保存的是选择，不保存成员关系和权限的最终判断。

未绑定组织的 API Key 只有在服务端明确声明个人空间仍可用时才能建立个人连接。个人空间关闭后，未绑定 Key 必须返回 `workspace_required`，提示创建绑定组织的 Key；客户端不能用 `personal:<user_id>` 伪装绑定结果。组织绑定 Key 固定在该组织空间，不能用 `--workspace` 或 `--all-workspaces` 扩大范围。

`org` 表达用户对组织的治理，不代表当前工作空间；`admin` 只表示显式的平台控制面。二者都不因为个人空间是否存在而改变权限边界。`apemind api` 和 MCP 调用沿用同一连接、同一工作空间选择和服务端实时授权。

## 服务端合同

所有接口继续使用 `/api/v2`。服务端必须保证：

- `/api/v2/me/workspaces` 只返回当前身份可访问的空间；个人空间只有在资格仍有效且迁移状态允许时才返回，空间可以为空；
- 工作空间相关读写每次校验成员关系、组织状态、资源权限和 API Key 绑定；
- 缺少工作空间的请求返回稳定的 `workspace_required` 或等价机器错误，不通过个人空间兜底；
- 个人空间关闭后禁止新建个人资源和未绑定个人 Key；已有数据只能通过迁移、导出或受控只读路径处理；关闭前仍存在的空个人空间不因为没有知识库而被客户端伪造或删除；
- 旧个人 Key 不得被解释成组织 Key，组织 Key 不得被解释成个人 Key；
- 缺失的 `personal_workspace_enabled` 状态按关闭处理，避免兼容投影意外重新开放个人写入；
- 站点管理员的控制面查询与普通用户的组织/工作空间查询分离，普通接口不返回全量平台组织。

个人空间删除、跨组织数据迁移和最终数据库清理不属于本阶段的隐式副作用。它们必须有单独的迁移计划、备份、回滚和人工验收。

## Desktop 行为

Desktop 登录页显示“可用工作空间”，不再承诺一定有“个人空间”。登录完成但列表为空时，页面应说明账号已经登录、当前没有可用工作空间，并提供刷新、加入组织或打开帮助的入口。工作空间选择器为空时，知识库、模型、Agent、Chat 和 Turn 的入口显示明确的“先选择工作空间”状态，不发送猜测请求。

Desktop 继续作为 CLI 的图形化语法糖：工作空间发现、选择、API Key 连接、错误码和刷新都调用同一套 CLI 合同。Renderer 不能自己拼接个人空间 ID，也不能把登录快照当作服务端权限证明。

## 实施计划

实施顺序按风险和依赖排列：

1. **合同收敛**：更新 CLI、Desktop、服务端和 MCP 文档；建立 workspace 状态、错误码、selector 和 OAuth scope 矩阵。
2. **CLI 登录与选择**：保存有效历史选择；只在明确条件下自动选择组织或遗留个人空间；支持空工作空间登录；删除所有合成个人空间的连接逻辑。
3. **API Key 边界**：根据服务端返回的绑定信息和个人空间状态建立连接；关闭个人空间时拒绝未绑定 Key；补齐账户级 Key 管理的提示和迁移信息。
4. **服务端默认值审计**：消除 `getattr(..., True)` 等隐式开放路径，检查认证依赖、模型、知识库、Bot、Chat、Turn、配额、导出和 MCP；每个 workspace-aware 路由都要在实际执行前完成空间校验。
5. **行为测试**：覆盖有个人空间、无个人空间、多组织、空列表、历史选择失效、未绑定 Key、组织 Key、跨空间聚合和部分失败。
6. **发布与过渡**：先在 staging 验证组织账户和历史账户，再发布服务端与 CLI；记录线上 `/api/v2/me/workspaces`、知识库读写、API Key 和 MCP 验收收据。个人数据迁移和删除另建项目，不随本次版本自动执行。

## 剩余工作与退出条件

当前版本只承诺兼容个人空间的三种真实状态：仍存在并可访问、存在但为空、已经不存在。服务端的 `personal_workspace_enabled` 只表示历史资格或迁移状态，Desktop、CLI 和插件 UI 都不能把它当作空间存在证明。剩余工作按以下顺序执行：

1. 服务端完成所有 workspace-aware 路由和初始化副作用的 presence 审计，尤其是 API Key、quota、Bot、tagging、widget、MCP、模型和历史恢复接口；个人空间缺失时在副作用前返回稳定的 `workspace_required` 或既有等价错误。
2. CLI 完成空列表登录、历史选择失效、组织绑定 Key、未绑定 Key 和 `--all-workspaces` 的行为测试；任何默认选择都只能来自 `/api/v2/me/workspaces` 返回的 canonical ID。
3. Desktop 完成有个人空间、空个人空间、无个人空间、迁移完成、多组织和无空间六种状态的界面与调用验收；Renderer 不拼接 `personal:<user_id>`，也不把登录快照当作授权证明。
4. 迁移项目单独提供导出、删除、回滚和执行收据。个人空间退出前不得以客户端升级或登录刷新代替数据迁移。

本阶段的退出条件是：上述六种状态在 staging 和目标生产环境都能通过 `/api/v2/me`、`/api/v2/me/workspaces`、知识库、模型、API Key、MCP、CLI 和 Desktop 验收；旧 flag 保留时仍不会恢复已迁移的个人资源；空列表登录成功但任何数据命令都明确提示先选择或加入工作空间。未满足这些条件时，工作只能标记为“合同已更新/实现进行中”，不能宣称个人空间退出已经完成。

## 与客户端发布的关系

Desktop 的发布不能把个人空间兼容逻辑隐藏在品牌插件内部。插件只消费 CLI/服务端返回的 canonical workspace 投影；服务端发布前必须先完成 presence、API Key 和初始化路径的合同测试，客户端发布前必须通过空列表和历史选择失效的 UI 测试。个人空间删除、导出和回滚不属于本次 Desktop 发布内容，必须由独立迁移项目提供收据后再安排最终清理。

## 验收标准

- 新 OAuth 账户只有组织空间时可以登录、选择组织并完成知识库读写；
- 历史账户个人空间被关闭后，登录不会显示或生成个人空间，旧选择会被清空或切换到唯一组织；
- 多组织账户不会被静默切错组织；
- 无工作空间账户登录成功，`workspace list` 可用，数据命令返回 `workspace_required`；
- 未绑定 API Key 在个人空间关闭时不能建立连接；组织绑定 Key 只能访问绑定组织；
- `--all-workspaces` 和 MCP 不会加入不存在的个人空间；
- Desktop、CLI 和直接 `/api/v2` 调用对上述状态给出一致结果；
- 关闭个人空间不会删除已有数据，迁移和删除操作有独立收据和回滚路径。

## 不解决什么

本文不决定是否永久删除个人数据、不设计新的组织邀请流程、不把 API Key 转换成 OAuth、不引入统一的 `task` 资源，也不要求 Desktop 维护第二套业务 SDK。所有高风险数据迁移、公开 API 破坏性变更和生产删除操作必须另行评审和授权。

## 读完后能回答的问题

- 为什么登录成功后可以没有工作空间？
- 客户端如何在个人空间存在与不存在之间保持兼容？
- 什么时候可以自动选择空间，什么时候必须让用户明确选择？
- 未绑定 API Key、组织 Key 和 OAuth 连接的边界分别是什么？
- 个人空间最终退出为什么不能通过一次客户端补丁完成？
